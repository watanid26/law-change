## 반드시 지켜야 할 것 3가지

오늘 실제로 사고를 낸 지점들이다. 설계에 안 넣으면 신규 소스에서 그대로 반복된다.

### 1. 보관 정책을 스키마 확정 시점에 같이 정한다

오늘 최대 비용 요인은 Compute도 Egress도 아니라 **버전 스냅샷 스토리지**였다. 조문 버전 750만 행 = 10.5GB.

정리를 시도해서 배운 것:

- 374분 걸려 640만 행을 지웠는데 **디스크는 안 줄었다**. Postgres DELETE는 공간을 OS에 반환하지 않는다 (`VACUUM FULL` 별도 필요)
- 지우는 과정에서 **상법·형사소송법·소득세법 등 38건의 조문이 통째로 사라졌다**

→ **사후 정리는 비싸고 위험하다.** 신규 소스마다 "몇 판까지 본문을 보관할지"를 처음에 정한다.

### 2. hash 비교에 바닥 검사를 넣는다

오늘 훈령 버그의 본질:

```
파서가 본문을 못 읽음 → 조문 0개로 저장 → contentHash도 0개 기준으로 계산
→ 재수집해도 "변경 없음" 판정 → 159건이 영구히 빈 채로 남음 (에러 0건)
```

→ **이전에 본문이 있던 문서가 이번에 0개로 파싱되면 "변경 없음"이 아니라 의심 건으로 격리.**

같은 이유로 hash 계산 범위는 **실제 저장 단위와 일치**해야 한다. 오늘 `computeDocumentHash`가 조문만 세고 전문은 빼고 있어서, 조문 없는 법령은 내용이 뭐든 늘 같은 hash가 나왔다. 이미 고쳤다.

### 3. unique key 조합은 표본으로 검증하고 정한다

이 프로젝트가 이미 두 번 물렸다.

- v13에서 `(문서, 일련번호)`로 부족해 **시행일**을 유일키에 추가해야 했다 (분할시행)
- `collector_job` 부분 유일 인덱스가 DEAD 잡 되살릴 때 충돌

→ "unique constraint + idempotent upsert"는 원칙이 맞고, **어떤 컬럼 조합이냐가 전부**다. 신규 3종 표본 검증 때 후보 키의 실제 유일성을 세어본다.

추가로 오늘 확인된 함정: **"최신 판"의 정의가 곳에 따라 다르면 조용히 데이터가 빈다.** 수집기는 시행일, 화면은 공포일 기준이었고 그 틈에서 38건이 증발했다. 신규 소스도 "최신"의 정의를 한 곳에 고정한다.

## 다르게 가는 것 2가지

### Lazy Loading을 REST 엔드포인트로 쪼개지 않는다

원칙(요청한 것만 내려보낸다)은 그대로 지킨다. 다만 이 앱은 Next.js App Router 서버 컴포넌트 구조라, 같은 효과를 **라우트 세그먼트 분리 + Suspense + 쿼리 분할**로 얻는다. `GET /laws/:id/articles` 같은 REST 층을 새로 만들면 아키텍처를 하나 더 늘리는 것뿐이다.

지켜야 할 것은 그대로다 — 요청하지 않은 과거 버전·전체 조문·전체 이벤트를 `SELECT *` 조인으로 한꺼번에 내려보내지 않는다.

### overlap 2~3일은 실측 후 정한다

법제처 지연 등록 실태를 아직 안 쟀다. `등록일 vs 공포일` 분포를 뽑으면 며칠이 적정인지 숫자로 나온다. 오늘 "30분이면 된다"고 추측했다가 실제로는 8시간이었던 일이 있어서, 이건 재고 정한다.

- **expc 우선** — LAW 데이터와 바로 결합되어 제품 가치가 즉시 올라간다. 다만 해석례↔법령 연결은 조문 참조가 문언 기반이라 **연결 품질 자체가 작업의 본체**다. 수집기는 쉬운 쪽
- 판례 17만 건 보류
- AI 초기 제외 — 영향평가는 사용자가 직접 입력
- 매일 06:30 1회, source별 checkpoint 분리, 실패 source는 checkpoint 유지

- 운영 주기: 매일 증분 / 매주 표본 정합 / 매월 전수 대조
