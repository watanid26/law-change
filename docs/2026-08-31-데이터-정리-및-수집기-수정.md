## 1. 행정규칙 본문 수집 버그 (국무총리훈령·대통령훈령)

### 증상

### 원인 (두 겹)

**(1) 응답 키가 다름**

법제처 API가 행정규칙 종류에 따라 본문을 다른 키로 준다.

```
고시·훈령·예규 대부분    AdmRulService.조문내용        → string[]
국무총리훈령·대통령훈령    AdmRulService.조문.조문내용   → 블록 안 병렬 배열
```

실측 (`ID=2200000107259`, 국무총리훈령):
```json
{"조문번호":["0001","0002",...],
 "조문내용":["제1조(목적) 이 훈령은 ...", "제2조(정의) ..."],
 "조문제목":[...]}
```

수집기는 `조문내용` 최상위 키만 읽었다.

**(2) 빈 판을 영원히 못 고치는 구조**

파서를 고쳐도 복구가 0이었다. `admin-rule-detail.ts` 는 판(`legalDocumentVersion`)이 이미 있으면 조문 생성 블록을 통째로 건너뛴다. 파서가 망가진 시절에 만들어진 "조문 0개" 판이 그대로 있으니, 재수집을 아무리 돌려도 계속 건너뛴다.

### 수정

## 3. 정리 과정에서 발생한 회귀 — 법률 38건 조문 전문 증발

### 무슨 일이 있었나

lawCheck는 한 문서의 "최신 판"을 **두 군데서 서로 다른 기준**으로 고른다.

| 위치 | 기준 |
|---|---|
| `src/lib/collector/detail.ts` | 시행일자 오름차순 정렬 후 마지막 |
| `src/lib/queries/lawDetail.ts` `getLawFullText` | **공포일 desc, 발령일 desc** 로 1건 |

정리를 **시행일 기준** 상위 3판 보존으로 돌렸다. 분할시행 법령에서는 두 기준이 어긋나, 화면이 고르는 판이 시행일 기준 4위 밖으로 밀린다. 그 38건의 조문을 지웠다.

포함된 법령: **상법, 형사소송법, 소득세법, 법인세법, 산업안전보건법, 국민연금법, 지방세법, 국세기본법, 항공안전법, 상법, 농지법, 화장품법** 등 — 전부 핵심 법령.

### 어떻게 찾았나
정리 후 전수 검증에서 "앱이 보여주는 판(rn_app=1)이 조문 0개인 문서" 764건을 발견. 이 중 정리 대상이었던(rn_prune>3) 것이 38건, 원래부터 비어 있던 것이 726건으로 분리됨.

### 복구
1. `src/lib/collector/detail.ts` 에 빈 판 자가 복구 추가
2. 단, 대상을 **`mustHaveContent`** 로 한정 — 양쪽 기준의 최신 판 + 같은 공포일을 가진 줄 전부
3. 38건 재수집

**조건 한정이 핵심이다.** 무제한 자가 복구를 넣으면 정리한 97,327판을 전부 다시 내려받아 작업 전체가 무효가 된다. 1차 시도에서는 조건을 수집기 기준 최신 판(`isLatestVersion`)으로 잡아 복구가 0건이었다 — 그 판은 정리 대상이 아니었기 때문. 화면 기준을 포함하도록 고쳐서 해결.

## 6. 판단 대기

### (a) `VACUUM FULL` — 완료

정리로 행은 87.9% 줄었으나 디스크는 그대로였다. Postgres는 DELETE로 공간을 OS에 반환하지 않는다. `VACUUM FULL` 로 회수했다.

| | 전 | 후 |
|---|---|---|
| DB 전체 | 14 GB | **4,500 MB** |
| `legal_content_unit_version` | 10 GB | **1,212 MB** |

소요 2.3분(예상 10~30분보다 짧았다). 실행 후 정확 카운트 대조로 손실 0 확인, 주요 화면 7개 실제 Chrome 렌더 확인(HTTP 200, 오류 0, 본문 길이 VACUUM 전과 동일).

**실행 시 걸렸던 문제**: Supabase의 statement_timeout(2분)에 걸려 90% 지점에서 취소됐다. 연결 문자열의 `options=-c statement_timeout=0` 은 Supavisor 를 통과하지 못한다. `DIRECT_URL`(세션 모드 5432) + `connection_limit=1` 로 물리 커넥션을 하나로 고정한 뒤 `SET statement_timeout = 0` 을 별도 실행하고, **같은 커넥션에서 실제로 0 인지 확인한 후** VACUUM 을 돌려야 한다.

주의: Supabase 할당 디스크는 자동 축소되지 않는다. **이번 달 사용량이 즉시 줄지는 않는다.** 효과는 (1) 앞으로의 디스크 자동 증설 차단, (2) 전체 코퍼스 수집용 여유 확보.

### (b) Spend Cap ON/OFF
현재 ON (한도 초과 시 서비스 정지). OFF면 초과분이 자동으로 청구된다.

**호스팅 비용을 최소로 유지하는 쪽(ON)으로 둔다.**

## 8. 검증 방법

추측이 아니라 실측으로 확인한 것만 위에 기록했다.

- 보존 대상 테이블은 통계 추정치가 아닌 **정확 카운트**(`count(*)`)로 대조
- 최신 3판 조문 보존 여부, 삭제 대상 잔존 여부는 **전수** 윈도우 함수 쿼리

- API 응답 구조는 **실제 호출**로 확인 후 수정

### 이 과정에서 저지른 실수
- 삭제 작업이 도는 중에 `count(*)` 전수 스캔 감사 쿼리를 걸어 두 번 타임아웃. 통계·표본 기반으로 전환
- 스크립트 로그가 UTC로 찍히는데 로컬 시각과 비교해 "9시간 정체"로 잘못 판단. 실제로는 19분 전 기록
- 정리 기준을 화면 기준과 대조하지 않고 실행해 38건 회귀 발생 (위 3장)

## 법령 연결은 AI 없이 된다

법제처 문서는 법령명을 「」 로 감싼다. 정규식으로 뽑아 제목으로 맞추면 된다. 실패하던 4건은 전부 **가운뎃점 문자 차이**였다 — 법령 DB 는 `ㆍ`(U+318D), 해석례는 `·`(U+00B7). 정규화하니 사라졌다.

## 증분 배치

날짜 창을 버렸다. 기존 `recentDays=45` 크론이 있었는데 2026-09-01 실측에서 **그날 개정 84건이 통째로 빠져** 있었다.

소스 성격에 맞게 둘로 나눈다.

- **법령·행정규칙** — 최신순으로 읽다가 아는 것이 200건 연속 나오면 중단. 행정규칙은 같은 날 발령분이 섞여 나와 연속 구간 최대가 40건이었다. 표본 300건만 보면 56건이던 누락이 끝까지 파니 72건이었다
- **해석례·결정문** — 전수를 8~20초에 훑는다. 해석례는 해석일자와 등록일시가 중앙 1,681일(최대 12년) 벌어져 날짜 기준이었으면 지연 등록분을 놓쳤다

**첫 실행에서 결함이 드러났다.** 행정규칙이 198초를 써서 해석례·결정문이 한 건도 못 돌았다. 원인은 항목마다 DB 를 두 번씩 조회한 것 — 100건이면 200번이다. 페이지 단위 일괄 조회로 바꾸니 법령 200건 스캔이 **29초 → 1초**가 됐다. 소스별 예산 배분도 함께 넣었다.

정상 상태 실측: **다섯 소스 전부 43초 · 중단 없음 · 수집 0건**(수렴 확인).

크론 `/api/cron/sync` 를 06:30 KST 로 걸었다.

## 사용자 안내

`/about` 페이지를 만들었다. 숫자는 DB 에서 세어 넣는다 — 문구에 박아두면 반드시 낡는다. **안 되는 것도 같이 적었다**: 첨부로만 오는 본문, 시행일 미정, 과거 판 전문 미보관, 이미지 별지 결정문.
